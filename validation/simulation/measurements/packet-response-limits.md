# Packet response-size accounting

Local evidence, 2026-09-25, macOS arm64. This is behavior evidence, not a
firmware memory, performance, or hardware qualification result.

## Change and independent regression

Packet ingress previously subtracted two bytes from every response value before
checking the caller's limit, while both Rust runtimes retained those bytes.
The new owner matrix and property test failed before the correction. Both new
mixed-runtime BLE scenarios also failed: Tokio accepted a 257-byte raw response
under a 256-byte bound, while Embassy refused it at its completion buffer.

Shared core now counts the complete encoded value after the outer request-ID
envelope. Tests cover raw and bin8/bin16/bin32-shaped values, malformed binary
prefixes, nil, zero/exact/overflow/unlimited limits, exact delivered bytes, receipt
retirement, duplicate settlement suppression, and later requests on the same link.
The mixed-runtime scenarios test both ESP32/Apple and nRF52/BlueZ endpoint pairs,
including exact 256-byte Embassy completion capacity. They use the existing
bounded queues and timeless polling budget.

The production change alters no wire bytes, retained state, queue limits, or buffer sizes.
Native and N-API clients still decode binary values after receipt; their packet
limit includes the encoded value header. C and N-API fixtures were updated to
that explicit contract, and N-API declarations were regenerated by its build.
Resource-envelope accounting remains an explicitly documented follow-up.
